## 坑 1：`pnpm dev` 报「node 不是内部或外部命令」

**现象**

在 VS Code 终端执行 `pnpm run dev`，报错定位在
`C:\Users\Administrator\AppData\Roaming\npm\pnpm.ps1:24`：
`无法将"node.exe"项识别为 cmdlet、函数、脚本文件或可运行程序的名称`。

**排查**

1. `where node` 没有任何结果 → 系统里根本没装 Node（只有工具自带的运行时）。
2. 顺手发现一个更隐蔽的问题：系统 PATH 里有一条畸形条目 `D:\Program Files (x86)"`（多了一个引号）。
   实测：即使把 node 所在目录加进 PATH，`cmd /c node -v` 仍然报「不是内部或外部命令」，
   而 `where node` 却能找到 —— 说明 **cmd 的可执行文件查找被 PATH 里的引号破坏了**。
3. 全局 pnpm 是 8.10.5，但项目 `pnpm-lock.yaml` 是 `lockfileVersion: '9.0'` → 版本不匹配，装完 Node 也用不了。

**原因**

- 没有系统 Node，pnpm 的 `.ps1` shim 依赖 PATH 里的 `node.exe`；
- Windows PATH 中含未配对的引号会让 `cmd.exe` 解析 PATH 异常（`where` 用的是另一套查找逻辑，所以能对上）；
- 项目 lockfile 是 pnpm 9+ 生成的，旧 pnpm 8 读不了。

**修复**

- 安装 Node.js LTS v24.22.1（MSI 校验 OpenJS 签名有效）到标准路径 `C:\Program Files\nodejs`；
- 全局 pnpm 8.10.5 → 11.28.5（匹配 lockfile 9.0）；
- 移除 PATH 里的畸形条目，并追加 `C:\Program Files\nodejs\`（修改前已备份原 PATH）。

**收获**

- `where xxx` 能找到 ≠ 一定能执行，二者查的不是一回事；
- 动 PATH 之前先备份；带引号的 PATH 条目是隐形杀手；
- 版本匹配要看 lockfile 的 `lockfileVersion`，不只看包管理器版本号。

## 坑 2：生成中一断网，页面只显示英文 `Failed to fetch`

**现象**

对话生成过程中按 F12 → Network → 勾 Offline，页面出现红字 `⚠️ Failed to fetch`，
没有重试入口，用户不知道发生了什么。

**排查**

阅读 `app/composables/useChatStream.ts` 的 `catch` 分支：断网时 `fetch` 抛的是
`TypeError: Failed to fetch`，它的 `name` 是 `TypeError`（不是 `AbortError`），
于是走到 `else` 分支，把原始的英文 `err.message` 直接显示到了页面上。

**原因**

1. 前端没有区分错误来源：用户主动停止（`AbortError`）、网络层失败（`TypeError`）、
   服务端错误（HTTP 状态码 + `statusMessage`）混在同一个分支里；
2. **流式响应的特殊之处**：`/api/chat` 一旦返回，HTTP 200 + 响应头就已经发出去了，
   之后上游出错 / 连接中断都**无法再用状态码表达失败**，错误语义必须在客户端自己设计；
3. 后来自己加的中文文案又把服务端已经归一化好的中文提示（如「API Key 无效…」）覆盖掉了。

**修复**

- 抽出纯函数 `toErrorMessage(err)`，三类错误分别处理：
  - `AbortError` → 返回空串（用户主动停止，不算错误）；
  - `TypeError` → 「网络已断开，恢复网络后请重试」；
  - 其他 → 透传服务端给的 `err.message`（auth / 余额 / 限流 / 5xx 的中文文案）；
- 保留已经流出来的内容，仅在「一个字都没生成」时移除空的占位气泡。

**收获**

- 浏览器 `fetch` 的网络失败是 `TypeError`，不是 HTTP 状态码层面的失败；
- SSE 场景下「HTTP 200 之后仍可能失败」，客户端必须自己定义错误与恢复策略；
- **错误码的知识放在服务端，客户端只处理错误语义** —— 以后换模型厂商，前端不用改；
- 把文案逻辑抽成纯函数后，可以直接写单元测试（后续接 Vitest）。

**待办**

- 加「重试」按钮（重发最后一条 user 消息，且不要把未完成的 assistant 半截消息带进上下文）；
- 用 `[DONE]` + `finish_reason` 判断「回答是否完整」，区分「正常结束」和「被截断」。

## 坑 3：回答不逐字出现，流结束后一次性蹦出来

**现象**

发送消息后 assistant 气泡一直是空的，直到流结束的瞬间整段回答一起出现；
内容变长时自动滚动到底部也不生效。看起来很像「网络慢」，其实是 bug。

**排查**

1. 先排除服务端：用脚本裸读 `/api/chat` 的 SSE，测得 14 个 chunk 在 658ms 内陆续到达
   （首字节 166ms）→ 服务端确实是渐进推送的，问题在客户端；
2. 用项目自带的 Vue 3.5 复现响应式行为：
   - 把普通对象 `push` 进 `ref([])` 后，**直接修改原始对象** → 不会触发重新渲染；
   - 通过数组代理修改 → 正常触发。

**原因**

`messages` 是响应式数组，模板渲染时拿到的是数组项的**响应式代理**；
而代码里 `const assistant = { ... }` 是普通对象，`assistant.content += delta`
改的是**原始对象引用**，Vue 追踪不到 → 流式期间不刷新，只有最后 `streaming/usage`
变化时才一次性渲染。

**修复**

占位对象用 `reactive()` 包一层，后续对它的写入才会被追踪：

```ts
const assistant = reactive<ChatMessage>({ role: 'assistant', content: '' })
messages.value.push(assistant)
```

（或者始终通过 `messages.value[i].content` 走代理写入。）

**收获**

- **进了响应式容器的对象，要改也得通过它的代理改**；
- 这类 bug 语法没错、逻辑看着也没错，错在**框架的响应式语义**，比语法错误更隐蔽；
- 排查顺序很重要：先证明服务端没问题（裸测），再怀疑前端。

## 附：本次弄懂的原理（不是坑，但值得记）

- **SSE 读取**：`reader.read()` 的 `done` 判断的是「传输层结束」；`[DONE]` 只是应用层的
  结束哨兵，不负责退出循环。两者结合才能判断「回答是否完整」。
- **chunk ≠ 行**：网络分块与行边界无关，要用 buffer 保留半行
  （accumulate → split → keep remainder）。
- **AbortController**：`controller.abort()` 发信号，`signal` 交给 `fetch` 订阅；
  取消时抛 `AbortError`；`signal` 一次性，下次请求要新建 controller。
- **streaming 是单一状态源**：驱动发送/停止按钮切换、光标、状态徽章、并发守卫；
  状态复位必须放 `finally`（成功/失败/中止三条路径都要解锁），
  但 `finally` 不防「流永远挂起」，需要超时兜底。
- **单飞（single-flight）模型**：生成中只能停止，不能发下一条；
  `controller / usage / error` 是单例共享状态 —— 这也是为什么去掉守卫后并发会互相覆盖。
